# Performance

What MinifyJS's performance looks like, how it is measured, and what
the numbers mean.

## The short version

MinifyJS is as fast as esbuild, because it *is* esbuild. The Go
binary calls esbuild's Go API in the same process, with no
intermediate serialization. There is no measurable overhead from the
wrapper.

For typical web application files, MinifyJS is roughly **20–40×
faster than terser** and **50–100× faster than uglify-js**.

## Startup time

Startup time matters when a build script invokes a minifier once per
file. For a project with 200 JS files, a 20 ms startup difference
adds 4 seconds to every build.

| Tool | Startup (median) |
|---|---|
| `minifyjs` | ~4 ms |
| `esbuild` | ~5 ms |
| `terser` | ~180 ms |
| `uglify-js` | ~250 ms |
| `rjsmin` | ~30 ms |

The exact numbers depend on the machine. The ordering is stable.

`rjsmin` starts quickly because it is a Python library, but its
throughput is far worse (see below).

## Throughput

For a ~50 KB input, minified to completion:

| Tool | Median time | MB/s |
|---|---|---|
| `minifyjs` | ~3 ms | ~17 |
| `esbuild` | ~3 ms | ~17 |
| `terser` | ~250 ms | ~0.2 |
| `uglify-js` | ~450 ms | ~0.1 |
| `rjsmin` | ~40 ms | ~1.3 |

MinifyJS and esbuild are the same because MinifyJS calls esbuild in
process. The 20–100× gap against the JavaScript tools is inherent to
the languages: V8's JIT is fast but not fast enough to close a
compiled-Go gap on this kind of workload.

## Compression

Smaller output is not always better. Compression has diminishing
returns and can interact badly with gzip or Brotli.

For a typical web application bundle:

| Tool | Output size | Ratio |
|---|---|---|
| `minifyjs` | 42 KB | 21% |
| `esbuild` | 42 KB | 21% |
| `terser` | 41 KB | 20.5% |
| `uglify-js` | 42 KB | 21% |
| `rjsmin` | 55 KB | 27.5% |

terser produces slightly smaller output because it is willing to do
more aggressive transformations. The difference is typically 1–3%,
and it comes at the cost of the 80× speed gap above.

`rjsmin` is 30% larger because it only removes whitespace and
comments. It does not mangle identifiers, fold constants, or
eliminate dead code.

## Memory

Peak RSS while minifying a ~500 KB file:

| Tool | Peak RSS |
|---|---|
| `minifyjs` | ~45 MB |
| `esbuild` | ~45 MB |
| `terser` | ~180 MB |
| `uglify-js` | ~220 MB |

MinifyJS's memory footprint is what esbuild's is, for the same
reason.

## How these numbers are produced

Every number in this file is generated by the benchmark suite in
[`bench/`](https://github.com/minifyjs/minifyjs/tree/main/bench).
The suite is reproducible: clone the repository, install the tools
you want to compare against, run `python bench/run_all.py`.

The output of the last official run is checked in at
`bench/results/latest.md`.

## What these numbers do not measure

- **Cold disk I/O.** The suite runs from a warm page cache.
- **Parallel execution.** Every measurement is single-threaded,
  because that is how a build script typically invokes a minifier.
- **Memory under concurrency.** The Python API is safe under
  parallel calls, but the peak memory measurement is from a single
  call.
- **End-to-end build time.** Only the minification step is measured.

## Caveats

**Absolute numbers are not meaningful.** They depend on the machine,
the OS, the filesystem, and what else is running. Only the relative
ordering between tools on the same machine on the same run is
meaningful.

**A faster minifier is not always a faster build.** If your build is
dominated by module resolution, transpilation, or bundling,
MinifyJS's speed advantage on the minification step will not move
the needle. Profile first.

**Compression is not the whole story.** An output that is 1% smaller
is not meaningfully better if it took 10× longer to produce.
MinifyJS is fast *and* competitive on size, which is the useful
combination.
