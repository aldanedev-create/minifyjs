# Benchmarking

How to run the benchmark suite and what to do with the results.

## The suite

The benchmark harness lives in `bench/`. It measures MinifyJS
against esbuild, terser, uglify-js, and rjsmin on four axes:

| Axis | Script |
|---|---|
| Compression | `bench/measure_compression.py` |
| Throughput | `bench/measure_throughput.py` |
| Startup | `bench/measure_startup.py` |
| Memory | `bench/measure_memory.py` |

Plus a runner that combines them:

```console
cd bench
python run_all.py
```

Output goes to `bench/results/latest.md`.

## Setting up

```console
cd bench
pip install -r requirements.txt
npm install
```

`pip install` installs `rjsmin` and `psutil`. `npm install`
installs esbuild, terser, and uglify-js into
`bench/node_modules/.bin/`.

The suite skips any tool that is not installed. MinifyJS is
required (the suite would be pointless otherwise). To compare
against all five, install all five.

## Running individual measurements

```console
# Compression ratios as a table.
python measure_compression.py

# Throughput on the medium fixture.
python measure_throughput.py --fixture medium.js

# Startup time.
python measure_startup.py

# Peak memory.
python measure_memory.py
```

## Fixtures

Six fixtures, of increasing size:

| Fixture | Approx. size | Purpose |
|---|---|---|
| `tiny.js` | < 1 KB | Startup overhead |
| `small.js` | ~5 KB | Single-file throughput |
| `medium.js` | ~50 KB | Typical application module |
| `large.js` | ~500 KB | Stress test |
| `application.js` | ~2 KB | Realistic multi-module shape |
| `real-world/` | varies | Real library files, not committed |

`medium.js` and `large.js` are generated by
`bench/fixtures/generate_medium.py` and `generate_large.py`.
Regenerate them if the schema changes:

```console
cd bench/fixtures
python generate_medium.py
python generate_large.py
```

Do not commit real library files (React, Vue, etc.) into
`fixtures/`. Put them in `fixtures/real-world/`, which is
gitignored.

## Methodology

Each measurement runs in a subprocess so JIT effects from one tool
cannot affect another. Each measurement warms up and reports the
median of several runs.

Defaults:

- Warmup: 3 iterations (ignored for measurement).
- Measured: 10 iterations.
- Reported: median.

Timing is wall-clock. CPU time would be more precise on a quiet
machine but is misleading on a loaded CI runner, which is where
most benchmark runs happen.

Memory is peak RSS. On Linux and macOS this comes from `getrusage`;
on Windows it comes from `psutil`.

## Reproducing the published numbers

The numbers in [`../performance.md`](../performance.md) come from a
specific run of the suite. To reproduce them:

```console
# Clone the same commit.
git checkout <the commit the numbers were measured at>

# Install every tool.
cd bench
pip install -r requirements.txt
npm install

# Run.
python run_all.py

# Compare your results/latest.md to the published one.
diff <(cat results/latest.md) <(git show HEAD:bench/results/latest.md)
```

Expect small differences. Absolute numbers depend on the machine.
The relative ordering should match.

## Interpreting results

### Compression

A smaller output is better. But beware:

- **Do not chase the last 1%.** If MinifyJS is 1% larger than
  terser, that is not a bug. It is a different tradeoff. terser is
  willing to do transformations that break obscure edge cases;
  esbuild is not.
- **Compression interacts with gzip and Brotli.** A 5% smaller
  JavaScript file can produce a *larger* gzipped bundle if the
  minified output has less repetition. Compression benchmarks are
  about raw JS size, not about what the user downloads.
- **`rjsmin` is not comparable.** It only removes whitespace and
  comments. Its compression ratio will always be worse. It is
  included as a baseline for Python users.

### Throughput

Higher MB/s is better. But beware:

- **The gap between MinifyJS and esbuild should be zero.** MinifyJS
  calls esbuild in-process. A measurable gap means the wrapper is
  doing unnecessary work.
- **Startup dominates for small files.** If your build script
  invokes MinifyJS once per file, startup time matters more than
  throughput. See the "Startup" table.
- **Throughput is not the same as build time.** If your build is
  dominated by module resolution, MinifyJS's speed on the
  minification step will not move the needle.

### Startup

Lower is better. This is the time from process spawn to process
exit for a trivial input.

Startup matters because a build script that invokes `minifyjs`
once per file pays the startup cost N times. A 20 ms startup
difference across 500 files is 10 seconds.

### Memory

Lower is better. But beware:

- **Peak RSS includes the Go runtime.** The Go runtime allocates
  memory eagerly and does not always return it to the OS. A 45 MB
  peak for a 500 KB input is normal.
- **Memory does not usually matter for a build tool.** Unless you
  are minifying on a machine with less than 1 GB of RAM, memory is
  not the constraint.

## Regenerating `latest.md`

```console
cd bench
python run_all.py
```

The suite overwrites `bench/results/latest.md`. Commit the change
if it is a release-time regeneration. Do not commit intermediate
runs; use `bench/results/history/` for those, which is gitignored.

## History

`bench/run_all.py` writes a timestamped JSON file to
`bench/results/history/` if `tools/benchmark_report` is set up. The
history directory is gitignored.

To compare the two most recent runs:

```console
go run ./tools/benchmark_report
```

Output:

```
comparing runs
  older: 2026-01-10T14:32:11Z (minifyjs 0.1.0)
  newer: 2026-01-15T09:11:04Z (minifyjs 0.1.1)

== compression
  tiny.js                 0.720 ->  0.720  (+0.0%)
  medium.js               0.210 ->  0.208  (-1.0%)
  ...

== throughput
  minifyjs                3.10 ->  3.05  (-1.6%)
  ...

no regressions above threshold
```

A regression greater than 5% flags with `<-- REGRESSION` and makes
the tool exit 1.

## Adding a new tool

1. Write `bench/compare_<tool>.py` with three functions:
   `is_available() -> bool`, `run(source: str) -> str`, and
   `run_timed(source: str) -> tuple[str, float]`.
2. Register it in the `TOOLS` list at the top of
   `measure_compression.py` and `measure_throughput.py`.
3. Add it to `measure_memory.py`'s `tools` list.
4. Add a row to the tables in [`../performance.md`](../performance.md).
5. Add it to the comparison table in `bench/README.md`.

The compare scripts intentionally do not share a base class. Each
tool has a different invocation shape (Node CLI, Python API, native
binary) and papering over that with an abstraction would hide
exactly the differences the benchmark is meant to expose.

## Adding a new fixture

Add a `.js` file to `bench/fixtures/`. If the fixture is generated,
also add the generator script and update this document.

Do not add more than one fixture of the same shape. Six fixtures
are enough. More fixtures means slower runs and more noise, not
more signal.

## Adding a new measurement

New measurements go in a new `measure_<name>.py` file. Each one is
self-contained: it imports the `compare_*` modules, calls
`is_available()` on each, and reports a table.

Wire the new measurement into `bench/run_all.py` by adding a
`capture("measure_<name>.py")` line to `main()`.
